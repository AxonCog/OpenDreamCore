# BMD 格式

两层：1 字节版本号 + 载荷。版本 1 = 裸二进制流；版本 2 = 载荷是 XZ 流（解压后是 v1 正文，
不含内层版本字节）。节点/材质名一律 UTF-16BE、U+0000 结尾；数值全大端。

## v1 正文布局

- short 节点数；每节点：short 自身 id、short 父 id（-1 = 根）、零终止名
- short 骨架组数；每组：short 条目数；每条目：short 骨骼 id +
  6 float 静止位姿（位移 xyz + 欧拉角 xyz，度）
- short 材质数；每材质：零终止名
- short 三角数；每三角：byte 材质索引；3 个顶点：
  short 保留、float x/y/z、float 法线 xyz、float u/v、
  byte 权重链长度、链 ×（short 骨骼 id、float 权重）

坐标约定：文件里 y/z（含法线）是 Z-up，入库取反换 Y-up；v 翻转为 1-v（左上原点）。
权重链最多收 4 根，超出部分按流读掉但不入库。

## 截断是常态

实测的宝可梦系列导出器写 XZ 流不写 index/footer，而且压缩数据本身也缺尾部
（15/15 个文件解压都在最后一个三角中途断流，charmeleon 1230 条三角实际只能
解出 1206 条）。这不是个别文件损坏，是导出器行为。

解析因此逐级容错：节点、骨架条目、材质名、三角任何一处读到流尾都停下，
能解多少入库多少，并在日志记一行截断位置。完整容器（带 index/footer）
走 XZInputStream 正常路径；截断流按 LZMA2 块头逐块直解。

## 动画

骨架段组数 > 1 时整体是一段帧动画：第 0 组仍是静止位姿，第 1..n 组为逐帧
全身骨骼姿态（20fps，循环）。帧转成统一的 AnimationIR（每帧一组
position + rotation 关键帧），之后的采样/混合/平滑与 bbmodel、bedrock
动画同一条路。

独立动画文件（idle.bmd、walk.bmd 这类）由资源扫描直接入动画池，
动画名 = 文件名去扩展名；EntityModel 规则的 `anims:` / `anim:` 按名引用即可。
真实宝可梦包验证：idle 15 帧 / walk 12 帧，骨骼名与网格文件一致，能直接驱动。

## 布局定案依据

对 charmeleon.bmd 的三角区做过全量约束验证：大端 float + 逐顶点
[short 保留 + 8 float + 权重链] 的组合能无残差连解 1206 条三角直到流尾，
材质索引恒 < 4、骨骼 id 恒 < 节点数、UV 全在 [0,1]——小端与其它字段顺序
的组合全部在数十条内崩掉。解析器以此为准。
